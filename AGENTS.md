# AGENTS.md

This file is the single source of truth for how any AI agent or developer writes code in UDM. Read it before making any change. Rules use MUST, MUST NOT and SHOULD in their usual sense.

The architecture below is the target. The code today is one crate that does not follow it yet. Section 16 lists where it deviates. New code MUST follow these rules. Existing code MUST NOT be restructured to match them unless a task asks for it.

## 1. Project overview

- UDM (Unified Download Manager) is a Rust desktop download manager that follows Internet Download Manager's behavior (see `GLOSSARY.md` for the names of its windows).
- It runs as three processes, plus a command-line tool and a server for AI assistants:
  - `udm-host`, the native-messaging host the browser launches. It relays browser messages to the daemon.
  - `udm-daemon`, the long-lived process that owns the download engine, so downloads outlive the browser.
  - `udm-gui`, the desktop window. It is a client of the daemon, like the host.
  - `udm-cli`, the command-line tool, another client of the daemon for terminals and scripts.
  - `udm-mcp`, the Model Context Protocol server that AI assistants start over stdio, another client of the daemon.
- The browser extension lives in `extension/` (JavaScript). It is outside the Rust architecture but speaks the protocol defined in Rust.
- Architecture: Hexagonal (Ports and Adapters) as a Cargo workspace, with a UI layer at the edge.
- UI framework: **egui**, through `eframe` 0.31 (glow/OpenGL backend, with AccessKit for screen readers), with `egui_extras` for the download table, `tray-icon` for the tray, and `rfd` (behind the `FilePicker` port) for native file and folder pickers.

## 2. Workspace layout

```
crates/
  domain/          entities, value objects, business rules, port traits
  application/     use cases that coordinate the domain through ports
  infrastructure/  adapters: file storage, HTTP/FTP engine, OS integration, IPC
  ui/              egui views, UI state, messages, event handling
  app/             binaries: udm-host, udm-daemon, udm-gui, udm-cli, udm-mcp (main.rs files, config, wiring)
```

How UDM's current concerns map onto these crates:

| Concern | Crate |
| --- | --- |
| Download states, queues and schedules, categories, file-name rules, batch URL patterns | `domain` |
| Add a download, pause, resume, run a queue, grab a site, export the list | `application` |
| HTTP/FTP transfers, HLS/DASH/HDS, settings and history files, DPAPI, registry, tray, toasts, power, recycle bin, browser registration, daemon IPC | `infrastructure` |
| Main window, save-as dialog, download windows, Options, translations | `ui` |
| Process startup, logging setup, wiring adapters to use cases | `app` |

The `app` crate MAY hold more than one binary (`[[bin]]` entries), since UDM ships five. Each binary is its own composition root.

## 3. Dependency rule

This is the most important rule. Dependencies point inward only.

- `domain` depends on nothing internal. Allowed external crates are pure ones such as `thiserror`, `uuid`, `chrono`, `url` (parsing only) and `serde` (derive only). It MUST NOT depend on `tokio`, `reqwest`, `rusqlite`, `sqlx`, `eframe`, `egui`, `windows`, `libc` or any other I/O, async runtime or UI crate.
- `application` depends only on `domain`, plus `tracing` for logging. It MAY start threads with `std::thread` (see section 5).
- `infrastructure` depends on `domain`, and on `application` only to implement a port that `application` defines.
- `ui` depends on `application` and `domain`. It MUST NOT depend on `infrastructure`.
- `app` depends on everything and is the only crate that wires concrete adapters into use cases.

| Crate | MAY depend on | MUST NOT depend on |
| --- | --- | --- |
| `domain` | pure crates (`thiserror`, `uuid`, `chrono`, `url`, `serde` derive) | `application`, `infrastructure`, `ui`, `app`, any I/O, async or UI crate |
| `application` | `domain`, pure crates, `tracing` | `infrastructure`, `ui`, `app`, I/O crates, UI crates |
| `infrastructure` | `domain`, `application` (ports only), I/O crates (`reqwest`, `tokio`, `windows`, `rfd`, ...) | `ui`, `app`, UI crates |
| `ui` | `domain`, `application`, `eframe`, `egui`, `egui_extras`, pure crates (`serde`, `serde_json`, `url`, `percent-encoding`, `thiserror`), drawing crates (`tray-icon`, `raw-window-handle`, platform crates under `cfg`) | `infrastructure`, `app`, I/O crates |
| `app` | every crate, `anyhow` | nothing is forbidden |

Platform-specific dependencies (`windows`, `libc`, `gtk`, `trash`) belong in `infrastructure` (or `ui`, when they only serve drawing, such as the tray or drag and drop) under `[target.'cfg(...)'.dependencies]`.

## 4. Domain layer rules

- MUST use newtypes for every meaningful value, for example `DownloadId(u64)`, `QueueId`, `ByteCount(u64)`, `Url`, `FileName`. MUST NOT pass raw `String`, `u64` or `i64` for domain concepts.
- Parse, don't validate. Constructors return `Result`, for example `FileName::parse(&str) -> Result<FileName, DomainError>`. A value that exists is always valid.
- MUST model states with enums so illegal states cannot be represented. A download is `Queued`, `Downloading { .. }`, `Paused { .. }`, `Complete { .. }` or `Failed { reason }`, not a set of booleans.
- Ports are traits defined here, for example `trait DownloadRepository: Send + Sync` and `trait Transfer: Send + Sync`.
- MUST NOT perform I/O, start threads, use an async runtime, read the clock or environment directly, or log. Time comes in as a parameter or through a `Clock` port.

## 5. Application layer rules

- One use case per file and struct, for example `AddDownload`, `PauseDownload`, `RunQueue`, `GrabSite`.
- Use cases are generic over ports (`AddDownload<R: DownloadRepository>`), or take `Arc<dyn Port>` when dynamic dispatch is needed.
- Use cases orchestrate. Business rules live in the domain.
- Input and output DTOs live here, not in `ui`.
- MUST NOT depend on the wire protocol's JSON shapes. Mapping protocol messages to DTOs is an adapter's job.
- MAY log with `tracing` and MAY run work on `std::thread` threads, such as a service that answers a request in the background. It MUST NOT do I/O itself: the work on those threads goes through ports.

## 6. Infrastructure layer rules

- Each adapter implements a port trait from `domain` (or from `application`).
- File formats, file paths, HTTP details, Win32 calls and the IPC wire format MUST NOT leak out of this crate.
- UDM stores its state in JSON files (`settings.json`, `history.json`, saved requests). Writes MUST be atomic (write to a temporary file, then rename). If a database is added later, its migrations live here and run at startup. Format changes to existing JSON files MUST read the old format.
- SHOULD use the `directories` crate for OS-specific data, config and log paths. MUST NOT hardcode paths or read `APPDATA`, `LOCALAPPDATA` or `XDG_*` outside the one module that resolves them.
- MUST map external errors (`io::Error`, `reqwest::Error`, `windows::core::Error`) into port error types at this boundary.

## 7. UI layer rules

- UI code is a thin adapter. It translates user events into use case calls and results into view state. MUST NOT put business logic in views, callbacks or update functions.
- MUST NOT block the UI thread. Daemon requests, file access and network work run on worker threads or tasks, and results come back as messages.
- Use unidirectional data flow: one state struct, changed only through messages.

egui-specific rules:

- Keep an `AppState` struct separate from the `eframe::App` implementation. `update` reads `AppState` to draw and turns clicks and keystrokes into `UiMessage` values. A single `apply(&mut AppState, UiMessage)` function changes the state.
- Talk to workers through channels (`std::sync::mpsc` or `crossbeam-channel`). Workers send results back and call `ctx.request_repaint()` so egui wakes up. `update` drains the channel with `try_recv`, never `recv`.
- MUST NOT call the daemon, read files or sleep inside `update` or any `show` function. egui calls these every frame.
- Every dialog and download window is drawn during the main window's frame (see `docs/adr/0001-cloak-the-main-window-in-the-tray.md`). Code that changes how windows are hidden MUST keep that frame running.
- User-facing text goes through the translation tables in `ui` (`crates/ui/src/lang/*.json`). MUST NOT hardcode English strings in views.
- A widget without text of its own (an icon, a symbol such as `×`, a hand-painted control or row) MUST get a name screen readers read, through `a11y.rs` and the translation tables. A key the window starts answering MUST be listed in `docs/keyboard-shortcuts.md`; a test in `help.rs` compares the page with the code.
- Before copying an IDM window, dialog or tray behavior, observe IDM first (the `observe-idm` skill in `.claude/skills/`). Learn IDM only by running it as a user does. MUST NOT decompile, disassemble or unpack IDM's files, extract their icons, dialogs or strings, or copy IDM's text or images into UDM. The one exception is UDM's logo, `assets/icon-1024.png`, which the project owner chose and which shows a globe, a ring and a green download arrow as IDM's logo does. Every icon file is made from it (`installer/render-icons.js`). No other image or icon design comes from IDM.

## 8. App (composition root) rules

- Each binary's `main.rs` loads config, initializes `tracing`, opens storage, runs any migrations, constructs adapters, injects them into use cases, and starts its loop (the egui window, the daemon's IPC server, or the host's relay).
- MUST NOT hold business logic.

## 9. Error handling

- Each layer has its own error enum built with `thiserror`, with `From` conversions between layers.
- `anyhow` is allowed only in the `app` crate.
- MUST NOT use `Result<_, String>` as an error type in new code.
- MUST NOT use `unwrap()`, `expect()` or `panic!` in non-test code, except for invariants that are truly guaranteed and documented with a comment next to the call. A poisoned mutex counts as such an invariant only when the comment says why.
- Errors shown to users are mapped to friendly, translated messages in the UI layer.

## 10. Async and concurrency

- SHOULD prefer generics (static dispatch). Use `Arc<dyn Trait>` only when needed, and `async-trait` for async traits used as trait objects.
- Shared services are wrapped in `Arc`. SHOULD avoid `Mutex` in domain and application code and prefer message passing.
- The engine runs async HTTP on one shared `tokio` runtime inside `infrastructure`. Other crates MUST NOT create their own runtime or depend on `tokio`.

## 11. Logging and observability

- Use `tracing` with structured fields, for example `tracing::info!(download_id = %id, bytes, "segment done")`.
- MUST NOT commit `println!`, `eprintln!` or `dbg!`. The exception is CLI output that is the program's actual output (the `udm-host` test mode, `udm-cli`). `udm-mcp`'s standard output is the protocol's alone, written by `udm_infrastructure::mcp`, so it never prints.
- Logs go to a file in the app's data directory. Logs MUST NOT contain cookies, passwords, auth headers or the daemon token. Download addresses are allowed, since the log is readable only by the user.

## 12. Testing

- Domain: pure unit tests, no mocks needed.
- Application: test use cases with in-memory adapters that implement the port traits.
- Infrastructure: integration tests against temporary files and directories (and a temporary database, if one is added), and against the local test HTTP server (today `crates/infrastructure/src/engine/testserver.rs`). The test server can also misbehave (`Behavior`: dropped connections, a limit per client, slow starts, wrong ranges, speed limits); tests of how the engine copes with a bad server use those faults. Tests MUST NOT reach the internet.
- Benchmarks: `tools/bench/` (Python, standard library only) times whole programs, UDM against IDM and others, on `tools/bench/faultserver.py`, which offers the test server's faults outside the tests. It is not a quality gate and is not shipped; its results go in `docs/bench/`.
- Every new use case MUST come with tests.
- Changes to the browser extension MUST pass `node --test extension/test/*.test.js`.

## 13. Quality gates

A task is not done until all of these pass:

- `cargo fmt --all --check`
- `cargo clippy --workspace --all-targets -- -D warnings`
- `cargo test --workspace`

CI runs them on Windows, macOS and Linux (`.github/workflows/`). Code under `cfg(windows)` or `cfg(unix)` is only checked on that platform, so state which platforms you could not build on.

## 14. Workflow rules for AI agents

- Read this file before making any change.
- Before writing code, state which layer or layers the change belongs to.
- Add a feature in this order: domain types and ports, use case, adapter, UI, wiring in `app`, tests.
- MUST NOT add a dependency without stating why and confirming it respects the dependency rule.
- MUST NOT restructure crates or move files unless explicitly asked.
- If a request conflicts with these rules, stop and explain the conflict instead of silently breaking the architecture.
- Run the quality gates and report the results at the end of every task.

## 15. Forbidden patterns

- Business logic in egui views, `update` or click handlers.
- Decompiling or extracting resources from IDM, or copying its text, icons or images. UDM's logo (`assets/icon-1024.png`) is the one image allowed to look like IDM's.
- I/O, threads, clocks or logging in `domain`.
- `ui` importing `infrastructure`.
- Blocking the UI thread, including daemon calls or file reads inside `update`.
- `unwrap()`, `expect()` or `panic!` in production code without a documented invariant.
- Hardcoded paths, or reading `APPDATA` and similar variables outside the path module.
- Raw primitives for domain concepts.
- `Result<_, String>` errors in new code, and `anyhow` outside `app`.
- `println!` and `dbg!` in committed code.

- **The daemon connection.** `udm_application::daemon` defines what clients send the daemon (`Command`) and what they hear back (`Event`), with a port on each side: `DaemonClient`, a client's connection (the window's, `udm-cli`'s and `udm-mcp`'s), and `Requests`, which the daemon's server hands each client's commands to, with a `Reply` for its answers. `udm_infrastructure::wire` maps both to and from the wire messages (`protocol::Incoming`, `Outgoing`); `daemon_client::IpcDaemonClient` implements `DaemonClient` over `ipc` and `protocol` (connection, handshake, `hello`); `new` hears what a window needs, `program` every event (`udm-cli` waits for `ack` and `pong`), and `assistant` every event but downloads' progress, which would pile up between `udm-mcp`'s requests. `udm_infrastructure::mcp` holds `udm-mcp`'s side of the Model Context Protocol (JSON-RPC 2.0 one message a line: `initialize`, `ping`, `tools/list`, `tools/call`) and its tools' names, descriptions and schemas: it maps each tool call to a `remote::Request` for the `Tools` port and each `Reply` to the tool's result, as `tool` does for the command line; it needs no MCP library. `udm_infrastructure::tool` holds `udm-cli`'s arguments, output and exit codes: it maps the command line to the `remote` use cases' requests and their results to text, as `wire` maps messages, and implements `remote::Watch` (`Terminal`). The documented part of the messages is the automation API (`docs/command-line.md`, `docs/automation-api.schema.json`, version `daemon::AUTOMATION_API`, sent in the daemon's `hello` as `api`); `infrastructure/tests/automation_api.rs` checks the schema against `protocol`'s messages. The download list's rules are in `udm_domain::table`, which the window feeds with `Event`s and the daemon (through `udm_infrastructure::state`) with wire messages. Its views reach the clock, the Downloads folder, the write check, opening and revealing files and the window's own files (`window.json`, `droptarget.txt`, through `udm_application::window::WindowFiles`, written on a thread by `udm_infrastructure::window_files::WindowDir`) through `ports.rs`' `Ports`, which `main` hands `udm_ui::run` in a `Start`. The grabber's projects, templates and filters (`GrabLibrary`), list import and export (`ListFiles`), the settings checks that read the disk (`SettingsChecks`) and the operating system's proxy, wake timers, sounds, credential store, fonts (the text and code fonts at start, and the font a language's script needs, for Chinese, Japanese, Korean or Vietnamese, which a worker reads when that language is chosen), capabilities and high-contrast colors (`SystemServices`; Windows' come from `SystemParametersInfoW` and `GetSysColor`, other systems have none), the theme files (`ThemeFiles`, `udm_infrastructure::themes::ThemeDir`, which reads the `key = value` `.theme` files in `paths::themes_dir`) and the file and folder pickers (`FilePicker`, `udm_infrastructure::pickers::NativePicker`) are ports in `udm_application::window` too. Browser registration is `BrowserRegistry` (`udm_infrastructure::browsers::Registry`), and the problem reports `ProblemReports` (`Ports::reports`); `udm-ui` does not depend on `udm-infrastructure`; `main` also builds the daemon client and hands it to the window. Workers read the grabber's projects and templates (every few seconds, every second while the grabber is open) and Options' browsers (when it opens) into `AppState`, and a thread runs `ReadThemes` every two seconds and sends its result when it changes (`UiMessage::ThemesRead`); each frame works out the look from it and the settings (`theme::appearance`) and restyles egui only when that changes; the category tree, the grabber's menus and Options draw from there. The grabber saves and opens projects, templates and filters, keeps a new password, Options identifies an added browser and opens the themes folder, and Save checks the settings on disk and registers browsers, each on a worker whose result a dialog takes with `pending.rs`' `Pending` (a one-shot channel read with `try_recv`). The Queues dialog's wake-timer check, Options' Get System proxy read and a batch's questions (the taken-name check among them) run on workers too, so the window reads the disk on its own thread only once at start, for its layout and the drop target's place.
- **Logic in the binaries.** None is left. The window's orchestration is in `udm-ui`'s `lib.rs` (about 5,300 lines), which a later split can break up. The daemon is done: `udm_application::daemon::service::DaemonService` does its work (each client's `Command`, the scheduler pass, the notification thread's `Note`s, start-up and idle checks) through ports, generic over a `Wiring` trait whose associated types name one adapter per port group. `src/bin/udm-daemon.rs` implements `Wiring`, builds the adapters (`new_daemon`), starts the background threads (`udm_infrastructure::background`) and serves clients (`udm_infrastructure::server`, which reads each frame as a `Command` for the service's `Requests` port, `Served`). Its behavior tests run the service on the real adapters.
- **GUI threads.** The GUI sends daemon work to `thread::spawn` workers. `state.rs` holds `AppState` (the list, the daemon's news and the threads' results), `UiMessage` and `apply`: the connection thread, the clipboard watcher, the tray menu and the failed-download timer send `UiMessage`s on a channel that `update` drains with `try_recv`, and nothing outside the frame changes the state. Those threads keep a `Watch` of the daemon's events (the settings, which downloads asked for a dialog or failed) to wake a hidden window, which on macOS and Linux gets no frames until it is shown. The frame changes `AppState` only through `apply` too: what it is done with is a `UiMessage::Forget`, and what it takes to show (the next completion dialog's news, the crawl's progress, picked links) a `UiMessage::Take`, which `apply` answers with what it took. The dialogs' drafts are view state: they live in `App` and their dialogs edit them in place, and a dialog's result is an `Action` that `App::perform` carries out (#199).
- **Errors.** The domain returns no `Result<_, String>`: its rules fail with `thiserror` enums (`QueueError`, `InvalidQueue`, `InvalidSettings`, `InvalidGrab`, `BatchError`, `CommandError`, `AddressError`, `FileNameError`, `DownloadError`, `UpdateError`, `ToolError`, `Mismatch`, `InvalidTheme`, `PairingError`, `PackageError`, `UnpackFailure`, `UnpackError`), as do the port errors (`ControlError`, `FilesError`, `SettingsError`) and the use case errors in `application::downloads` (`StartOrWaitError`, `ConfirmError`). The daemon service's commands fail with `udm_application::daemon::service::ServiceError`, which wraps the use cases' errors. The window translates the domain's enums in `udm-ui`'s `errors.rs`. The daemon tells clients of a failure with `udm_application::daemon::Failure` (`Event::Error`, `Rejected`, `Update`, `UpdateFailed`, `ZipPreview`, `LinkInfo`, `RefreshMismatch`, and `DaemonError::Refused`): a `ServiceError` or `SettingsError`, a new link's `udm_domain::download::Mismatch` (which the engine's `partial_matches` and the `check_partial` port return), an unreadable message, a probe's own words, or `Other` for text alone. `udm_infrastructure::wire` sends each as its English text, as before, for the clients that do not translate (the browser extension, `udm-host send`), plus an `error_kind` with the error's kind and values, which mirrors the application's enums around the domain's (these derive `serde`, so their variant names are wire format, pinned by `wire`'s golden tests); a message without a kind it can read (an older daemon's, or a newer kind) becomes `Other` with the text. The window translates every one (`errors::daemon`). A download's own failure (`Event::Failed`, kept in the list) and why a crawl stopped (`GrabDone`) are still English text from the engine and the crawler. `anyhow` carries the binaries' startup errors in `app` and nowhere else. `infrastructure` has an enum per module (`HlsError`, `DashError`, `HdsError`, `FfmpegError`, `CliError`, `ImportError`, `ZipError`, `ReleaseError`, `ScanError`, `NotifyError`, `EditError`, `TransferError`, `SaveError`, `settings::CheckError`, `EngineError`, `MoveError`, `web_remote::certificate::CertificateError`, `web_remote::http::ReadError`), which keep an `io::Error`, `serde_json::Error` or `windows::core::Error` as their source where there is one. Port errors that are still a message (`ControlError`, `ProbeError`, `FilesError`, `ListError`, `SettingsError::Refused`) carry those enums' text. No function returns `Result<_, String>`. Why a theme file gives no theme is a `udm_application::window::ThemeFileError` (with the line and the domain's `InvalidTheme`), which `errors::theme_file` translates for Options. `ui` fails with `UiError`, a message for the user that the domain's enums turn into through `From` (translating them), and the tray with `TrayError`. Most modules return `io::Result`.
- **unwrap and panics.** None are left outside tests but documented invariants: the workspace's clippy lints (`[workspace.lints.clippy]` in the root `Cargo.toml`, which each crate takes with `[lints] workspace = true`) warn on `unwrap_used`, `expect_used`, `panic`, `todo`, `unimplemented` and `unreachable`, so the quality gate's `-D warnings` refuses them, and `clippy.toml` lets tests (`#[cfg(test)]` modules, test-only modules such as `memory.rs` and `testserver.rs`, and `#[test]` functions) unwrap, expect and panic, and each crate and binary root lets tests use `todo!`, `unimplemented!` and `unreachable!` (`#![cfg_attr(test, allow(...))]`), which clippy.toml cannot exempt. A documented invariant is an `expect("why")` with a comment stating it and a local `#[allow(clippy::expect_used)]`; eight are left, at seven sites (the installed ports in `udm-ui`'s `ports.rs`, HMAC keys in `dpapi.rs` (two) and `ipc.rs`, piped child output in `engine/page.rs` (stdout and stderr in one statement) and `media/convert.rs` (two)). Poisoned locks have one policy, `udm_domain::sync`: `LockExt::lock_or_recover`, `RwLockExt::read_or_recover` and `write_or_recover`, and `recover` for a `Condvar` wait, take the guard back, because every lock guards plain data, a panic in the middle of a change leaves at worst stale bookkeeping, and the panic is already in the log. It is in `domain`, the one crate every layer depends on, as pure `std` code without I/O; the modules' own lock helpers call it. CI lints the Windows and macOS code; with those targets added through `rustup`, `cargo clippy --target x86_64-pc-windows-gnu` or `--target x86_64-apple-darwin` lints it from Linux too.
- **Logging.** The five binaries log with `tracing`. Each `main` calls `udm_infrastructure::logging::init`, which writes `udm-daemon.log`, `udm-host.log`, `udm-gui.log`, `udm-cli.log` or `udm-mcp.log` in the data folder (`paths::daemon_log`, `host_log`, `gui_log`, `cli_log`, `mcp_log`), appending each line in one write so many hosts can share a file, and hides passwords in addresses; a server's daemon (`udm-daemon --server`) calls `logging::init_stdout` instead, which writes the same lines to standard output. The daemon moves a log over 5 MB to `.old` once it wins the bind and then hourly; the host also writes warnings to standard error, which the browser reads. Each `main` then calls `udm_infrastructure::crash::install`, a panic hook after `logging::init`'s that writes a problem report (version, system, install, the panic, its backtrace, the log's last lines, scrubbed of the token, passwords, cookies and authorization headers) to `paths::reports_dir`; the window's watchdog thread (`udm-ui`'s `watchdog.rs`) writes one when a frame stops and pings the daemon to see it answer, and the window offers reports through `UiMessage`s (`docs/problem-reports.md`). The release profile strips debug info but keeps symbols, for the backtraces. `domain` does not log; `application` logs in the daemon service, `remote::Assistant` and the report use cases. The `eprintln!` and `println!` calls left are `udm-host`'s `download` and `send` modes and `udm-cli`'s report (with `tool::Terminal`'s progress on standard error), `udm-daemon`'s `--help`, `--version` and command-line errors, whose output is the program's actual output, and three in tests. Event fields log ids as their numbers (`download_id = id.get()`) and addresses as their text.
- **Paths.** `udm_infrastructure::paths` resolves every folder UDM uses (settings, data, grabber projects, theme files, the logs, the problem reports, the window's files, the sign-in entry, app packages' AppData copies and browser profile roots) on top of `directories`' `BaseDirs`, and is the only module that reads `APPDATA`, `LOCALAPPDATA`, `USERPROFILE` or `XDG_*` (`desktop_session` reads `XDG_CURRENT_DESKTOP` and `XDG_SESSION_TYPE` for problem reports). On Windows it reads those variables before the known folders, because end-to-end runs point them at a scratch folder, and on Linux it uses any non-empty `XDG_CONFIG_HOME` and `XDG_DATA_HOME` as given (`directories` ignores relative ones), so no folder moved. It also reads a server's folders, `UDM_CONFIG_DIR`, `UDM_DATA_DIR` and `UDM_DOWNLOADS_DIR` (`paths::Folders`), which `udm-daemon --server`'s `--config`, `--data` and `--downloads` (`daemon_args`, handed to `paths::choose_folders` first thing) override; a folder named so is used as given, ahead of a portable copy's and the system's (`docs/server.md`). It also resolves `remote_dir` (the remote-control page's certificate and paired devices, in the data folder). It also owns `UDM_INSTANCE` (`paths::instance`) and portable mode (`paths::portable_root`): a `portable.txt` beside the programs, or above `target\release` as in the portable zip, puts the settings and data folders, the window's files and the engine's default parts folder (`paths::parts_dir`, otherwise `UDM` in the system's temporary folder) in the copy's `Data` folder and the default Downloads folder beside it (`docs/portable.md`); `autostart`, `notify::register_app` and `from_old_names` (which moves what Pullbay and UIDM, UDM's earlier names, left) then leave the system alone, `browsers::register_found` runs on Windows too, and the window learns of it through `SystemServices::is_portable`.
- **Raw primitives.** Ids (`udm_domain::id::{DownloadId, QueueId}`, `udm_application::daemon::ClientId`), byte counts (`udm_domain::bytes::ByteCount`, saturating), download addresses (`udm_domain::address::{Address, Link}`) and file names (`udm_domain::filename::FileName`) are newtypes through the domain, the ports, the use cases, `Command` and `Event`, `protocol` and the window. Each serializes as the plain number or string, so `history.json`, the saved requests, settings, grabber projects, list files and the wire keep their shape (tests in `history` and `protocol` pin it, and `wire`'s golden `error_kind` JSON is unchanged). `Address` is what the daemon takes, `http://`, `https://`, `ftp://` or `ftps://` in any case (`batch::is_download_url`, with `batch::is_ftp_url` for the two FTP schemes), kept as given; `Link`, a download's address as a client sent it or a file holds it, is an `Address` or other text, so a refused request still decodes (and is `rejected` by name) and an old row still loads. `FileName` refuses empty names, `.`, `..`, `/`, `\` and NUL; `sanitize_filename`, `name_from_url` and `proposed_name` return one. What stays raw: the engine's insides (`u64` counters, offsets and sidecars, and `DownloadRequest`'s address and name), converted where they meet the domain (`app::to_request`, `progress_to_outgoing`, `Inspection`, `fetch`); a client's request numbers; speeds and the settings' KB and MB fields; connection counts (the settings', an entry's, and a `Download`'s own `connections`, which `Download::connections_or` brings into range); addresses that are not a download's (referrers, pages, `PageLink`, proxies, the grabber's `GrabRequest` and `GrabFile`, stream segments); names as typed or sent (`Download::filename`, `Answer::filename`, `Properties::filename`), which are cleaned into a `FileName` when used; error values that echo what was refused (`NotDownloadAddress`, `NotDownloadLink`), whose wire shape is pinned; and paths.
- **Storage.** State is JSON files, not SQLite. Section 6 is written for files. Nothing needs to change unless a database is added.
